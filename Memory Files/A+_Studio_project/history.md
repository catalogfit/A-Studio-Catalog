## Session update — 29 Oct 2026 (v0.2: backend + clean FINAL template + category routing)

### 8. Template backend (design files per category)
Built `backend/` — a tiny Node server (`server.js`, no dependencies) that stores one **manifest per category/template** under `backend/templates/` (the "design file"), served over HTTP:
- `GET /api/templates` → the registry (`index.json`: categories, their templates, and the global sheet schema).
- `GET /api/templates/running/template-1` → the Running manifest.
The plugin pulls from this when a backend URL is set; otherwise it uses the copy bundled into `plugin/code.js` (auto-generated from the same files by `plugin-src/build-fallback.js`, so the offline copy never drifts). Add a category → add a manifest file + a registry row.

### 9. Clean FINAL Running template, built on Figma Page 2
Analysed the whole `706524` template frame (`616:2514`) and the real finished designs group-by-group. Both were carrying the **mask-layer mess**: 2 stacked photos inside single circle masks, ~20 leftover mask groups piled in the same 4 positions on the real `706524`, a hidden leftover rectangle, a fixed-height fabric copy box, and stale layer names ("COMFORT" showing RUN).

Built **`RUNNING – Template 1 (FINAL)`** (node `651:2`) on Page 2:
- Hero **cloned from the real template** so it keeps `image 396` (7% texture), the `Ellipse 86` glow, both grads, and the exact RUN / UNSTOPPABLE treatment; layer `COMFORT` renamed `Hero word`.
- Fabric icons **cloned from the real template** (real Sweat-Wicking / Lightweight artwork, not generic rings).
- Every circular photo is a **real Figma mask group** — `mask` (isMask ellipse) + `Photo` rect + dashed `placeholder ring` + label — exactly like `706524`, so a dropped photo clips to the circle. One photo per mask, nothing stacked.
- Each callout is grouped as `Card N` = Bar + Mask group + Text; fabric/callout copy is auto-height; 2 export slices.

The plugin renderer (`plugin-src/renderer.js`, `photoSlot`) now outputs the same mask-group structure, so generated A+ match the template.

### 10. Column B = Category (routing)
The content sheet gained a **Category column (B)**. New layout: **A Style IDs · B Category · C Card 1 Hero (optional) · D Card 2 Fabric · E–H Cards 3–6.** The plugin reads column B per row and builds that row with the matching category's template — so one sheet can mix Running, Training, etc. Rows whose category has no active template yet (e.g. Training) are reported row-by-row instead of failing the batch. The category buttons in the UI are now just the default for rows that leave column B blank. Schema lives in `backend/templates/index.json → sheet` (with `categoryAliases`), bundled into the plugin fallback too.

## Session update — 2 Nov 2026 (Google OAuth + premium UI)

- **Why "Publish to web → CSV" was needed:** the plugin UI reads the sheet with a plain `fetch` and
  no Google sign-in, so it could only reach a publicly-exported CSV; a normal Sheets link returns
  HTML / is CORS-blocked (hence the "Could not read that link" error).
- **Google OAuth added** (`backend/google.js`, pure Node, no deps): auth-code flow with token refresh
  and per-session storage in `backend/.data/` (gitignored). New routes in `server.js`: `/auth/new`,
  `/auth/callback`, `/auth/status`, `/auth/logout`, and `POST /api/sheet` (reads any sheet the user
  can open via the Sheets API). Config via `backend/.env` (see `.env.example`); a tiny built-in
  `.env` loader means no dependency. Scopes: Sheets read-only + Drive file + email.
- **Plugin:** "Connect Google" flow — opens the consent URL, polls `/auth/status`, stores an opaque
  session id (`clientStorage`), then **Load** reads a normal Google Sheet link through the backend
  (falls back to the CSV method when not connected).
- **Premium UI redesign** (`plugin/ui.html`): gradient logo + header, Google/Backend status pills,
  rounded card sections, category chips, segmented sheet control, gradient Run button, collapsible
  Backend & connection panel. Theme-aware via Figma color tokens.
- **Still to do:** the user must create a Google Cloud OAuth client (Sheets+Drive APIs, redirect
  `…/auth/callback`) and paste the id/secret into `.env`. Drive **export** is the next piece.

## Session update — 26 Nov 2026 (v0.3: gender routing, inherited manifests, fit comparison, selection rebuild)

### 11. Templates are routed category → gender → template
The registry (`backend/templates/index.json`) moved to `"schema": "aplus.registry/2"`. Each category
now carries a `genders[]` array, each gender its own `templates[]`, and each category a
`defaultGender` for rows that don't name one. A template entry can declare
`"features": ["fitComparison"]`. Manifest keys became `"<category>/<gender>/<template>"`, e.g.
`running/women/template-1`. Four Running templates are active: `running/men/template-1` (Standard),
`running/men/template-2` (With fit comparison), and the same pair under `running/women/`.

### 12. Manifests can `extends` another manifest
The shared Running geometry lives in `backend/templates/running/_base.json`; each gender template is
a thin file that sets `"extends": "running/_base"` and overrides only `meta`, the hero model slot
label and `comparison.enabled`. New `backend/manifests.js` resolves the chain with a deep merge
(objects merge, arrays replace) and exposes `load`, `resolve`, `registry`, `findCategory`,
`findGender`, `findTemplate` — so the plugin and the renderer still only ever see one flat manifest.
The old `backend/templates/running/template-1.json` and its `.preview.svg` were deleted.

### 13. New backend routes
`backend/server.js` gained `GET /api/templates` (the registry: categories → genders → templates),
`GET /api/templates/:category`, `GET /api/templates/:category/:gender` (that gender's template list),
`GET /api/templates/:category/:gender/:template` (the resolved manifest) and
`…/preview.svg` (optional; none shipped yet). The Google OAuth routes (`/auth/new`,
`/auth/callback`, `/auth/status`, `/auth/logout`, `POST /api/sheet`) are unchanged.

### 14. The content sheet gained two columns
New layout: **A Style IDs · B Category · C Gender · D Card 1 Hero · E Card 2 Fabric · F–I Cards 3–6 ·
J Fit comparison.** Gender accepts men / women / unisex, and may also be written into column B
("Running Women") with C left blank. Column J holds two lines — the left and right fit labels
(e.g. "Regular fit" / "Slim fit"); blank means the template's defaults. A row with anything in
column J is routed automatically to a template with the `fitComparison` feature, even if a different
template is selected in the panel. New workbook `sheets/A+_Running_Content_Template_v2.xlsx`
(tabs "RUNNING — content" and "How to fill"), with a header row 1 and a "FORMAT — …" hint row 2,
both skipped by the parser.

### 15. The fit comparison card
`plugin-src/renderer.js` gained `buildComparison(M, F, parent, labels, topY)`, which draws the card —
two labelled photo slots plus alignment guides — when `manifest.comparison.enabled` is true; the
frame grows by `comparison.gap + comparison.h`. `addComparisonToFrame(M, F, frame, labels)` adds the
same card to an **already-built** frame, growing the frame, the background gradient and the trailing
export slice — the manual escape hatch for when the content sheet doesn't carry the fit detail.
`rowFromManifest` now also returns `cmp: { labels: [left, right], fromSheet: boolean }`, and
`frame.bottomPad` is manifest-driven (it was hardcoded 108.76).

### 16. The plugin panel is now a 4-step flow
`plugin/ui.html`: **1 Category → 2 Gender → 3 Template → 4 Content.** Step 3 shows a **live preview**
of each template, drawn as SVG straight from the manifest, so a thumbnail can never drift from what
gets built. Step 4 has three sources: **Sheet link**, **Paste rows** and a new **Selection** tab — in
Selection mode the plugin reads the six-digit style IDs off the frames selected on the canvas,
matches them against the loaded sheet rows, and rebuilds those styles on the category/gender/template
picked in steps 1–3 (the picker overrides columns B and C). A collapsible
"✚ Add a block to the selected frame" panel offers **Add fit comparison**, with editable left/right
labels.

`plugin-src/main.js` gained a `selection` message pushed on load and on every `selectionchange`
(reporting the selected frames and the style IDs read from their names, or from a style-ID text label
sitting just outside the frame), a `ping-selection` handler and an `add-comparison` handler. `init`
now also sends `manifests: FALLBACK_MANIFESTS`, so the UI can draw previews with no backend running.

## 19. The template was missing most of the real graphics — fixed

Rohit compared the first skeleton against 706524 and said a lot of graphical elements were missing.
He was right. Extracting every non-photo layer from the real design showed the manifest was carrying
a simplified cartoon of it:

| Real layer | What the template had |
|---|---|
| `image 396` hero texture (image fill at 7%) | nothing |
| two large rotated `grad` washes on the body | nothing |
| hero `Ellipse 86` radial glow | nothing |
| two hero `grad` layers (−18.27°, −41.88°) | one approximated "shade" at +16° |
| fabric `grad` wash (21.25°) | nothing |
| `Rectangle 42167`, a 35% wash over the fabric photo | nothing |
| four glow ellipses — **radial gradients** | solid white ellipses with a 160px layer blur |
| background gradient — 3 stops on a rotated matrix | 4 stops, plain top-to-bottom |
| `Vector 87` divider — gradient stroke fading at both ends | flat white rectangle |

The root cause was the manifest's paint model: it only supported three fixed gradient directions
(`TB`/`LR`/`RL`), with no radial gradients and no image fills, so anything else had to be faked.

**What changed**

- `paintOf()` in `renderer.js` now takes a full paint spec — `{solid}`, `{image, scale}`, or
  `{stops, gt, radial}` where `gt` is a raw Figma `gradientTransform` matrix. Arbitrary gradient
  angles now survive into the template instead of being flattened.
- `shape()` and `drawLayers()` render an ordered stack of decorative layers. `background.layers`,
  `hero.layers` and `fabric.layers` replace the old `gradientRect` / `glows` / `shade` / `overlay`
  fields. An entry with a `role` (`word`, `italic`, `model`, `tagline`, `bgPhoto`, `closeup`) is a
  hole in the stack where live content is dropped, so **z-order now lives in the manifest**.
- `yFromBottom` anchors a layer to the frame's bottom edge and `hToFramePlus` stretches it to the
  frame, so both survive a 3-callout design and the taller fit-comparison one.
- Image fills are checked with `figma.getImageByHash` and dropped with a warning when that image is
  not in the open file (an image hash only resolves inside the document holding the bytes).

**The flip bug.** After the first rebuild two washes still landed in the wrong corner, even though
their `x`, `y`, `width`, `height` and `rotation` all matched the original exactly. Comparing bounding
boxes showed why: `Hero shade · bottom` and `Wash · fabric` are **flipped as well as rotated** —
their transform matrices have a negative determinant, which a rotation angle cannot express. Layers
now carry `rt`, the full Figma `relativeTransform` matrix, which reproduces rotation and flips
exactly. Every graphical layer in the rebuilt skeleton now matches the real 706524 to within 1px
(the residue is rounding from storing the matrices to three decimals).

All four templates were rebuilt on Page 2 and verified against 706524 — see §20.

## 21. RCA — "image 396 is still missing"

Rohit reported the texture was still absent after §19. Two subagents did a read-only layer-by-layer
diff of all four generated templates against the real 706524 (men) and 706327 / 706591 (women),
and the node data was checked directly.

### Finding: the layer was never missing

In all four templates `image 396 · texture` existed with the **identical** image hash
(`28773688…`), the same `FILL` scale mode, the same **0.07** paint opacity, the same box
(−1085.19, −66.69, 2961.45 × 1681.68), `visible: true`, no hidden ancestor.
`figma.getImageByHash` resolved it to the same 2881 × 1636 / 159,883-byte image as the original.
So the complaint was correct about the symptom and wrong about the cause: it was **present but
invisible**.

### Root cause — three compounding faults

1. **No hero backing plate.** The real hero's bottom-most content is a full-bleed photograph
   (`706524_C exp 1`, 1825 × 2102; the women's equivalent `8p 1` / `10p 1` is 1614 × 1614). The
   template had no such slot at all, so the hero was a near-white void. A 7% dark texture over a
   near-white ground is invisible; over the mid-grey photograph it reads as the dot grid you can
   see in the original. **This was the dominant cause.**
2. **Z-order inverted.** The template drew `Hero shade · bottom` *above* the texture. In the
   original the texture sits above that shade. The shade was therefore washing out what little of
   the texture was visible.
3. **The model slot was the wrong shape** — 640 × 1486 at x 420, where the original's model
   occupies 1039 × 1408 at x 268 — so the hero read as an empty column rather than a composition.

### Everything else the diff turned up

| Finding | Status |
|---|---|
| Hero backing plate slot absent (men **and** women) | fixed — new `bgPhoto` role in `hero.layers` |
| `image 39x` below the bottom shade instead of above | fixed — stacking order now taken from each original |
| Model slot 640 × 1486 → should be 1039 × 1408 at (268, 122) | fixed |
| `Photo wash` rendered, but **switched off** in both originals | fixed — layers now support `"visible": false` |
| Women's hero bottom shade is **white**, template used near-black | fixed in `_women.json` |
| Women's Fabric veil is **white @0.35**, template used red-black @0.52 | fixed |
| Women's hero right shade rgb(72,72,74), template used rgb(28,26,31) | fixed |
| Women's fabric close-up is Ø503.63 at (534.19, 1666.94) with a white ring; template had Ø426 at (571, 1734) and no ring | fixed — new `ring` role |
| Women's hero stacks the plate bottom-most and the texture *below* the bottom shade | fixed — women's own order |
| Fit comparison guides: 2 verticals + 2 horizontal rows of two offset spans, #AAAAAA at 3.685px; template had 1 vertical pair + 1 full-width bar at 55% | fixed — real geometry |
| Fit photo slots 597.5 wide with a 40px gap; originals are 666.95 wide and **overlap by 98.65px** | fixed — originals' geometry |
| `Vector 87` divider "missing" | **false positive** — it is a RECTANGLE named `Divider` inside `Card 2 · text` with the identical gradient; the agent searched for VECTOR nodes at the top level |
| Second 481px mask group in the real fabric card | **not reproduced, deliberately** — it is one of the orphaned mask groups this project set out to clean up |

### The bigger correction

The earlier claim that "men's and women's share the same geometry and palette" was **wrong about
the palette**. They share the geometry; the art direction differs. Worse, some of it is per-style,
not per-gender: 706327's hero shade is grey (72,72,74) while 706591's is lavender (200,174,225),
matching its product photography. A template cannot fix that — so the gender templates carry the
gender-consistent values and the per-style colour is left for the designer to change.

That is why `running/_women.json` now exists: it extends `running/_base.json` (which holds the
shared geometry and the men's art direction, measured off 706524) and overrides only what the
women's files genuinely do differently.

### New manifest capabilities this needed

- `"visible": false` on a layer — reproduce a layer the original has switched off.
- `hero.bgPhoto` + a `bgPhoto` role in `hero.layers` — the full-bleed backing plate.
- `fabric.ring` + a `ring` role — the women's white ring around the close-up.
- `comparison.label.xs` / `comparison.photo.xs` / `comparison.guides.vertical[]` /
  `.horizontal[]` — explicit positions instead of derived ones, so the card matches 706327 exactly.

### Verified after the fix

All four templates rebuilt. Hero stacking matches its own reference layer for layer; the texture
box is identical to the original's to the pixel; the fit-comparison card and its guides match
706327's `Group 862` exactly ([237, 4774, 1235, 990], photos at x 0 and 568); the men's close-up is
426 at (571, 1734) and the women's 504 at (534, 1667). No missing fonts, no warnings.

## 22. RCA round two — the texture was rendering the wrong way

Rohit sent the actual PNG of `image 396` and said "something different is coming". Correct again.

Dumping **every** enumerable key of the image paint (rather than the ones assumed) found two
properties that had been dropped:

| Property | Real 706524 | What was generated |
|---|---|---|
| `scalingFactor` | **0.5** | 1 |
| `filters.exposure` | **-1** | 0 |

Same bitmap, same hash, same 0.07 opacity, same box — but drawn at **twice the dot size** and
**without the darkening**, so the halftone read as a different texture entirely.

Cause: `paintOf()` built image paints from `{type, imageHash, scaleMode, opacity}` only, letting
Figma default `scalingFactor` to 1 and every entry in `filters` to 0. It now carries
`scalingFactor`, `rotation`, `imageTransform`, `blendMode` and the full `filters` object, and the
manifests record `"scalingFactor": 0.5, "filters": { "exposure": -1 }` on the texture layer.

Verified by diffing the rebuilt paint against the original key by key: **identical**.

The general lesson, now true four times over: *fidelity fails in the properties you did not think
to copy.* Capture generically, never with an allow-list. This is written up as the central
argument of `docs/add-to-template-plan.md`.
